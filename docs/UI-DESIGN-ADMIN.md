# CodePaint Studio 招新成员后台 UI 设计

> 应用：`apps/admin-web`  
> 面向：招新成员 `recruiter`  
> 详细规范：见 [UI 设计总览](./UI-DESIGN.md)

---

# 1. 产品任务

后台不是传统 HR 数据大屏，而是一个让招新成员快速处理报名材料的工作台。

核心问题：

- 新报名是否已收到；
- 哪些材料还在解析或解析失败；
- 报名者适合哪个招新方向；
- AI 为什么给出某个匹配结果；
- 下一步是复核、联系、补材料还是归档。

体验关键词：安静、高密度、可扫描、可追溯、操作明确。

# 2. 页面与路由

```text
/workspace
├── /dashboard
├── /inbox
├── /applicants
│   └── /applicants/:applicant_id
├── /roles
├── /jobs
│   └── /jobs/:job_id
├── /templates
│   ├── /templates/:template_id
│   └── /templates/:template_id/versions/:version
├── /tasks
└── /settings
    ├── /settings/members
    ├── /settings/email
    ├── /settings/ai
    ├── /settings/ocr
    └── /settings/storage
```

所有 `/workspace/*` 路由必须要求 `recruiter` 角色。没有权限的用户不能通过手动输入 URL 访问页面。

桌面端：

```text
┌──────────────┬────────────────────────────────────┐
│ CodePaint    │ 页面标题 / 面包屑 / 页面操作         │
│ 招新概览      ├────────────────────────────────────┤
│ 报名收件箱    │ 内容区                               │
│ 报名者        │                                    │

│              │                                    │

```

- Sidebar：`232px`；
- 内容最大宽度：`1280px`；
- 页面背景：`#FFFFFF`；
- 分区使用边框和留白，不使用大面积阴影；
- 当前导航项使用 `#EEF7FF` 背景和天蓝色短线；
- 主操作优先使用黑底白字，品牌操作使用淡蓝底深蓝字。

## 3.1 Header

左侧显示页面标题和必要的面包屑，右侧提供：

```text

```

全局搜索快捷键为 `⌘ K`，但快捷键不能作为唯一入口。小于 `960px` 时 Sidebar 收起为 Sheet。

# 4. 核心页面

## 4.1 招新概览

不做复杂 BI，只展示待处理事项：

```text
招新概览

[待查看 12] [解析中 4] [解析失败 1] [本周新报名 21]

最近报名
姓名 / 意向方向 / 来源 / 状态 / 时间

待处理任务
解析失败 / 待人工复核 / 待联系
```

数字模块使用紧凑边框区域，不使用四个巨大彩色卡片。点击数字应进入对应筛选结果。

## 4.2 报名收件箱

```text
报名收件箱                         [搜索] [筛选]
──────────────────────────────────────────────
● 林同学       工程       resume.pdf       待查看
  你好，我想参与 CodePaint 的工具开发。       8 分钟前

○ 周同学       设计       portfolio.pdf   已解析
                                             昨天
```

列表必须显示：姓名或发件人、意向方向、附件、收到时间、解析状态、已读状态。支持批量标记已读和进入报名者详情。

## 4.3 报名者列表

推荐使用类似 Linear 的高信息密度列表：

```text
报名者                              [搜索] [筛选]
──────────────────────────────────────────────
□ 林同学   工程   2 年经验   Go · React · PostgreSQL   89
           上海   近期报名   强匹配

□ 周同学   设计   学生       Figma · Branding           82
           杭州   近期报名   合适
```

筛选项：

```text
意向方向 / 状态 / 城市 / 经验 / 技能 / 匹配度 / 标签
```

筛选条件使用 Chip + Popover，例如：`[方向：工程] [匹配度 ≥ 80]`。不要默认使用复杂可编辑表格。

## 4.4 报名者详情

```text
← 报名者

林同学                                      待联系
工程 · 上海 · 2 年经验
[标记为已联系] [查看原始材料]

┌──────────────────────────┬───────────────────────┐
│ 报名信息                  │ AI 辅助复核             │
│ 自我介绍                  │ 匹配度 89               │
│ 教育 / 经历 / 项目         │ 命中：Go、React、Postgres │
│ 技能                      │ 缺少：公开作品链接       │
│ 作品链接                  │ 理由与依据               │
│ 原始材料                  │ 模板与解析版本           │
└──────────────────────────┴───────────────────────┘
```

AI 结果必须包含：命中项、缺失项、判断依据、模板版本、模型信息和原始材料入口。匹配分析是辅助判断，不得显示为自动录取结论。

## 4.5 原始材料预览

原始简历、作品集和邮件来源是第一等公民：

- 支持预览、下载和新窗口打开；
- 文件访问先经过 API 权限校验，再返回短期签名 URL；
- 解析字段旁可以回到原文上下文；
- 原始文件不能被解析结果覆盖；
- 查看和下载都记录审计事件。

## 4.6 解析历史

```text
解析历史

v3  工程方向模板       provider-model   已完成   今天
v2  通用报名模板       provider-model   已完成   昨天
v1  通用报名模板                         已完成   8 月 28 日
```

点击版本可查看结构化字段差异。重新解析必须产生新的 ParseRun，不覆盖历史结果。

## 4.7 处理任务

```text
处理任务

✓ 林同学_resume.pdf       已完成
◌ 周同学_portfolio.pdf     正在 OCR
✕ 王同学_resume.pdf        解析失败       [重试]
```

详情显示处理阶段：

```text
读取材料 → 提取文字 → OCR → AI 分析 → 校验 → 完成
```

失败状态需要说明用户可执行的动作，不只显示错误码。

## 4.8 模板与邮箱设置

模板编辑器使用三栏布局：字段列表、字段编辑、材料预览。已激活版本不可直接覆盖，只能创建新版本。

邮箱设置集中处理 IMAP 配置、连接测试和手动同步。密码不回显，敏感操作需要明确反馈。

# 5. 交互规范

## 5.1 状态

报名状态建议：

```text
新报名 / 处理中 / 待复核 / 待联系 / 沟通中 / 已归档 / 不合适
```

状态必须同时有文字和非颜色提示。状态变更记录操作者、时间和备注。

## 5.2 Loading / Empty / Error

- 使用局部 Skeleton，不使用整页 Loading；
- 空状态必须给出下一步，例如“还没有报名者，先分享公开报名页”或“连接报名邮箱”；
- 解析错误展示“重试解析”“重试 OCR”等上下文动作；
- Toast 只用于轻量反馈，复杂错误保留在页面上下文内。

## 5.3 工具按钮

下载、打开新窗口、重试、筛选、搜索、批量操作使用熟悉图标。图标按钮必须有 Tooltip 和可访问名称，不用文字胶囊替代明显的工具图标。

# 6. 响应式与验收

断点：`Desktop ≥ 1200px`、`Tablet 768–1199px`、`Mobile < 768px`。

- Sidebar 在 Tablet / Mobile 收起为 Sheet；
- 报名者详情双栏改为上下分区；
- 原始材料预览作为独立 Tab 或全屏 Sheet；
- 列表支持横向信息压缩，但不出现页面级横向滚动；
- 模板编辑器桌面优先，移动端至少支持查看和修改基础字段；
- 成员能在三次操作内从概览进入待处理报名；
- 成员能从报名者详情看到 AI 依据和原始材料；
- 普通用户无法通过 URL、接口或猜测资源 ID 访问后台数据；
- Desktop、Tablet、Mobile 不发生文字、按钮和列表重叠。
